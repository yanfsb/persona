# Managed command surface

Persona adapters intentionally support a bounded grammar. This is a guide to the documented surface, not a promise to emulate every Git or GitHub CLI feature. Check `persona --help` and repository tests for the current exact grammar. Unknown, ambiguous, or unsupported forms are refused in managed scopes.

## Git

The managed Git adapter supports selected local operations including safe-pathspec `add`, scoped `status`, bounded `diff`/`show`, restricted `rev-parse`/`log`, branch/tag/worktree listing, selected local branch/worktree operations, `init`, policy-identity commits, and constrained fetch/clone/pull/push forms. Remote transport is limited to exact configured destinations using managed HTTPS or SSH. Ordinary `git fetch` resolves the current branch's configured remote, falling back to `origin` only when it exists; `git pull` resolves the current branch's explicit upstream. `git push` honors the branch push remote, configured push default remote, and supported `push.default` modes (`simple`, `upstream`, or `current`); modes requiring multiple or implicit refspecs are refused. Missing or ambiguous metadata is refused rather than guessed. `git fetch --all` preflights every Git-eligible remote (respecting `remote.<name>.skipFetchAll`), requires one exact profile-bound destination for each, then runs each through its managed HTTPS or SSH transport. Configured fetch refspecs are preserved; `FETCH_HEAD` entries are combined. Pruning occurs only when explicitly requested with `--prune`; tag pruning and recursive submodule fetching are disabled so remote-specific Git config cannot introduce unpreflighted side effects or destinations. A missing/unauthorized remote blocks all network activity, while a runtime transport failure can leave earlier successful remotes fetched and still returns failure. Multiple effective URLs per remote and unsupported options are refused. Same-name push refspecs are canonicalized before policy checks. For HTTPS, Git credential-protocol metadata is ignored unless needed to identify the exact HTTPS host and repository; caller-supplied credentials never replace the profile-bound account token. The managed Git child receives only the resolved absolute `gh` executable path, not the caller's `PATH` or `HOME`. Push is bounded by ref count, ref kind, configured policy, available object/signature evidence and, for rewrites/deletions, exact expected remote OIDs. See the [implementation matrix](implementation-matrix.md) and tests before relying on a particular subcommand form.

An optional per-profile `[profiles.git.commands]` table restricts supported operations: `allow` is an allowlist when present, `deny` is an additional denylist and wins on overlap. `allow = []` denies all; missing `allow` preserves the existing supported surface. Semantic selectors include `fetch.all`, `branch.list`, `branch.create`, `tag.signed`, and `worktree.add`; broad `fetch` includes `fetch.all`, and deny `fetch` blocks both. Lists cannot enable unsupported command forms or bypass destination, account, identity, signing, or publication checks.

The bounded GUI-compatible surface includes common status/branch display flags and fetch/pull flags such as `--prune`, `--no-tags`, `--quiet`, and `--verbose`; it does not emulate every Git option. Unsupported examples include arbitrary helpers/protocols, mirror/follow-tags/submodule modes, implicit or unbounded refspecs, and force updates without an exact lease plan. Some enabled policy options intentionally remain unusable where a complete transport path is not implemented.

## GitHub CLI (`gh`)

The managed `gh` adapter supports an explicit allowlist on GitHub.com, including selected repository and PR/issue/release view/list/create operations, typed PR checkout/review/merge, and constrained repository-scoped REST requests. The profile must bind the selected account and explicitly allowlist a repository for protected operations. Enterprise hosts, extensions, arbitrary methods/headers/inputs and unrecognized commands are refused.

PR checkout requires a clean worktree, fetches a specific PR head through managed transport, checks the fetched commit against API metadata, and refuses branch collisions/hooks that it cannot safely handle. Server-side merges require a separate explicit repository/base/strategy grant; the resulting server commit is not represented as locally signed. Release creation requires an already-published locally verified signed annotated tag, checks the remote tag before/after, and never creates or pushes that tag. The API does not atomically bind tag name to object ID, so a concurrent retag race can only be detected afterward.

### Release asset upload

`persona run -- gh release upload TAG FILE... --repo OWNER/REPO` uploads to an existing release only after the same enrolled-account, repository, publication-destination and signed-annotated-tag checks used by release creation. The remote tag must match the locally audited tag before and after upload. Upload never creates a release or tag.

Supply one to eight explicit regular files within the selected physical Git worktree. Files are read through no-follow directory/file descriptors and snapshotted before credential selection or network activity. Limits are 64 MiB per file and 128 MiB total. Basenames must be unique (case-insensitively), at most 255 ASCII letters/digits or `.`, `_`, `+`, `-`, and cannot be `.`, `..`, or begin with `-`. Symlinks, paths escaping the worktree, directories, stdin, globs, labels and `--clobber` are refused. Review the actual asset contents before publishing; confinement does not establish that a file is safe to disclose.

The uploader requires curl 8.3 or newer, disables curl configuration and inherited proxy settings, and sends snapshotted bytes only to the fixed HTTPS GitHub upload endpoint. All redirects are rejected; the selected token is never placed in command-line arguments. Returned asset IDs, names, sizes, states and supplied SHA-256 digests are validated.

Uploads are sequential and non-transactional. Existing names are refused, assets are never overwritten/deleted, and failed requests are not automatically retried. An error identifies confirmed uploads and any uncertain asset. Inspect the release before retrying only missing assets: a timeout or server failure can leave an uploaded or empty `starter` asset. There is no managed asset deletion/replacement command. Pre/post tag checks detect a retag afterward but cannot prevent the provider's concurrent-retag race. Older/missing curl fails the upload rather than enabling native passthrough. These restrictions do not enable generic `gh api` headers, file inputs, or arbitrary upload URLs.

## Hooks, PATH and shell

`persona run` adds temporary managed Git/gh shims for that invocation; it directly spawns the program without an implicit shell and preserves argv, cwd, stdio and exit status. Persistent adapter links are separately installed into an existing user-owned bin directory. Persona does not edit shell startup files. The optional Zsh prompt hook is visual convenience only.

A pre-push hook is repository-local, separately installed and composable only for supported configurations. It is a second barrier, not a replacement for the pre-transport adapter. `--no-verify`, direct native binaries, another network client, or a hostile same-user process can bypass managed paths; see the [security model](security-model.md).
